# Ревью: ядро цикла, состояние и данные (коммит f9edc3e)

Что прочитано полностью: `main.gd`, `main_input.gd`, `profile.gd`, `report.gd`, `settings.gd`, `input_setup.gd`, `loc.gd`, `campaign.gd`, `run_log.gd`, `telemetry.gd`, `tuning_panel.gd`, `class_task.gd`, `prog.gd`, `demo.gd`, `story.gd`, `hints.gd`, `project.godot`, `main.tscn`, `export_presets.cfg`, начало и конец `tuning.gd`. Выборочно: `main_debug.gd` (вход, автотест, тесты отчёта и выхода), `cards.gd` (`offer`, `apply`), `plane_classes.gd` (шапка, список функций), `hud_screens.gd:12-80` (экран выбора), `hud_hangar.gd:35-55`, `menu.gd:60-80`, `tools/ci/smoke.sh`, `full.sh`. `perf.gd` — только список членов.

### Сильные стороны

- **Профиль пишется через временный файл**: `.tmp`, потом `rename` (`profile.gd:171-178`). Загрузка накрывает значения по умолчанию значениями из файла по ключам (`profile.gd:149-168`): новые поля появляются сами, старый профиль без `crew_rank` переводится без потерь (`profile.gd:162`). Вычисляемое (уровни, очки перков) не хранится.
- **Настройки загружаются с `clampi` по каждому полю** (`settings.gd:304-315`): битый или старый `settings.json` не приводит к выходу за пределы массивов.
- **Вычисляемое отделено от хранимого**: все покупки идут через пары `can_* / *` (`profile.gd:428-495`), и каждая сама проверяет условия. UI не может купить в обход.
- **Демо-режим сделан одной точкой** (`demo.gd`): потолки (`node_cap`, `tier_cap`, `crew_cap`) читаются в `Profile` и `Campaign`, сохранение полного прогресса не трогается.
- **Отчёты устойчивы к отсутствию сети**: очередь на диске, досылка при запуске (`report.gd:73-76`), очередь строк вылетов ограничена (`RUN_QUEUE_MAX`, `report.gd:429`), отправка не блокирует игру.
- **Хорошая наблюдаемость**: строка лога с версией набора колонок в имени файла (`run_log.gd:16`, `Telemetry.LOG_VER`), поминутная шкала, замеры FPS и отрисовки раз в 15 кадров, а не каждый кадр (`telemetry.gd:113`).
- **Перевод продуман**: ключ — русская фраза, шаблоны с числами переводятся до подстановки (`loc.gd:1-8`), есть разбор склеенных строк (`Loc.out`, `Loc.title`) с кешем и его ограничением (`loc.gd:22`).
- **Модули Main вынесены**: `MainInput`, `MainDebug`, `RunLog`, `Telemetry` — `RefCounted`-объекты с явной ссылкой `m`, а не узлы-синглтоны.
- **Физические клавиши** (`input_setup.gd`): WASD работает на любой раскладке. Скрипты экспортируются в бинарных токенах (`script_export_mode=2`).

### Проблемы

#### Критические (чинить обязательно)

1. **Игра может застрять на экране выбора карточек без выхода** — `main.gd:425-427`, `main.gd:455-458`, `main.gd:505-522`.
   - **Что не так.** В `choose_card` при `pending_levels > 0`, в `choose_course` и в `ban_card` новый набор берётся из `Cards.offer(...)`, а пустой результат никак не обрабатывается. Случай «все улучшения собраны» обработан только в `_open_levelup` (`main.gd:394-403`).
   - **Когда случается.** Если последняя доступная карточка взята, а в очереди ещё есть уровни (уровень и награда за активность в один момент — обычное дело к концу вылета), состояние остаётся `levelup` с `offers = []`. Второй путь: игрок исключает единственную оставшуюся карточку, а замены нет. В состоянии `levelup` `handle_global_input` выходит рано (`main_input.gd:56-63`): Esc, пауза и Tab не работают, а `hud_screens.gd:12-60` рисует пустой экран без кнопки «продолжить».
   - **Чем грозит.** Вылет теряется вместе с наградой. Выйти можно только закрыв окно.
   - **Как чинить.** Одна функция `_refill_offers()`. Если набор пуст, она проходит ту же ветку «ремонт и запчасти» и возвращает `playing`. Вызывать её из всех четырёх мест, включая `reroll`. Плюс проверка в autotest: принудительно опустошить пул карточек.

2. **Профиль может пропасть насовсем, и игрок ничего не узнает** — `profile.gd:139-178`.
   - **Что не так.** Результат `DirAccess.rename_absolute` не проверяется. На Windows Godot сначала удаляет `profile.json`, потом переименовывает. Если переименование не прошло (антивирус, блокировка файла), остаётся только `profile.json.tmp`. `load_profile()` про `.tmp` не знает: при следующем запуске профиль пуст, и первая же покупка или вылет перезаписывает всё.
   - **Второй путь.** Если JSON не разобрался (`d is Dictionary` ложно, `profile.gd:147`), игра молча стартует с нуля, и следующий `save()` затирает испорченный, но, может быть, спасаемый файл.
   - **Что ещё.** `VERSION := 1` пишется, но нигде не читается, механизма миграций нет. Типы при загрузке не проверяются: `var src: Dictionary = d["classes"][c]` (`profile.gd:155`) упадёт, если там не словарь. `data["weapons"][w] = d["weapons"][w]` (`profile.gd:168`) копирует без проверки.
   - **Почему критично.** Для раннего доступа потеря сохранения — самый частый повод для отрицательного отзыва.
   - **Как чинить.** Общий `SaveIO`: запись в `.tmp`, проверка `store_string` и `rename`, хранение `.bak` от прошлой удачной записи. При загрузке порядок `profile.json` → `.tmp` → `.bak`. Битый файл переименовывать в `profile.broken-<время>.json`, а не затирать. Миграции по `version`.

3. **Строка каждого вылета уходит на сервер сама, без согласия, и в демо тоже** — `report.gd:412-432`, `main.gd:83`, `main.gd:115`.
   - **Что уходит.** `REPORT_URL` берётся из `REPORT_URL_BUILTIN` в любой сборке, включая `demo` и будущий релиз. `queue_run` при каждом конце вылета отправляет в Google Таблицу ОС, видеокарту, экран, постоянный `tester_id` (`report.gd:329-342`) и полную строку лога. Галочки согласия и отключения нет.
   - **Расхождение с решением.** В плане демо записано «кнопка с согласием игрока, политика конфиденциальности» (`docs/demo-next-fest.md:8`, DM-07), а в коде автоматическая отправка ничем не ограничена. Постоянный идентификатор вместе с IP по GDPR — персональные данные.
   - **Риск масштаба.** Публичное демо — тысячи игроков: Apps Script и лист таблицы упрутся в квоты.
   - **Как чинить.** До выпуска демо: флаг `Settings.telemetry_ok` (по умолчанию выключен вне тестерских сборок), экран согласия, отправка только при согласии. Для `demo` и релиза — отдельный адрес приёмника или его отсутствие.

#### Важные (стоит чинить)

4. **Подсказки новичку «сгорают» до первого вылета** — `main.gd:237-243`, `hints.gd:172-184`.
   - **Что не так.** `start_run()` вызывается не только для вылета, но и для фона меню: `_ready`, возврат из ангара, смена района на заставке (`main_input.gd:25`, `:171`, `:316`). `Hints.show` сразу увеличивает счётчик `seen` и сохраняет его, а следующий `start_run` очередь сбрасывает (`Hints.clear()`).
   - **Пример.** Подсказка `controls` (`times = 2`) получает один показ уже на заставке при первом запуске, второй — в вылете. Если игрок до вылета дважды зашёл в ангар или переключил район, подсказка про управление не покажется никогда.
   - **Почему важно.** Удар по обучению — ровно то, что будут смотреть игроки демо на Next Fest.
   - **Как чинить.** Показывать подсказки старта вылета из `select_class` и `restart`, а не из `start_run`. Либо считать показ в `Hints._next()`, когда текст действительно вышел на экран, и только в состоянии `playing`.

5. **Папка сохранений зависит от названия проекта** — `project.godot:8`.
   - **Что не так.** `config/name="Flak Heaven - Prototype 3 (3D)"` без `use_custom_user_dir`, а Godot строит `user://` из названия. Переименование под релиз («Flak Heaven») переносит профиль, кампанию и настройки в новую пустую папку.
   - **Почему важно.** Тестеры теряют прогресс, а обещанный перенос «демо → полная игра» (`demo.gd:6`) ломается.
   - **Как чинить.** Сейчас, пока название не трогали: `application/config/use_custom_user_dir=true`, `custom_user_dir_name="FlakHeaven"`. Плюс одноразовый перенос из старой папки.

6. **Номер сборки в репозитории устарел и правится руками только при экспорте** — `main.gd:81`.
   - **Что не так.** В коде `BUILD := "3.4-t1"`, а по `docs/status-log.md:193,198` номер (`3.5-s9`, `3.5-s10`) меняется «только в экспорте». От него зависят имя файла лога (`run_log.gd:16`), поле `build` в отчётах (`report.gd:376,420`) и версия в меню (`menu.gd:334`).
   - **Чем грозит.** Забыли поменять — отчёты тестеров и строки вылетов попадают в таблицу под чужой сборкой, а разбор плейтеста идёт по неверным данным.
   - **Ещё.** Версии в пресетах экспорта (`0.3.3.1`, `export_presets.cfg:33-34,107-108,174-175`) тоже устарели, иконки нет (`application/icon=""`).
   - **Как чинить.** Номер сборки — коммитом перед экспортом (или из `ProjectSettings application/config/version`, одно место), проверка в скрипте сборки, что номер не совпадает с прошлым.

7. **Одна смена громкости «замораживает» баланс на диске** — `tuning.gd:186-213`.
   - **Что не так.** `save_params()` пишет все параметры, включая баланс, а вызывают её смена громкости и схемы в меню (`menu.gd:108-210`) и F9 (`main_input.gd:126`). При следующей сборке старые значения баланса подхватятся из `tuning.json`, если не увеличен руками `VERSION := 15` (`tuning.gd:7`).
   - **Чем грозит.** Тестер играет на старом балансе, и это не видно ни ему, ни в логе.
   - **Отладочные значения тоже утекают на диск.** Ключи запуска меняют параметры через `set_param`: `--shots` → `boss_hp=300` (`main.gd:135`), `--tilt` (`main.gd:123`), `--warship` → `boss_every=60` (`spawner.gd:40`). Если в том же сеансе что-то вызовет `save_params`, значение попадает на диск.
   - **Как чинить.** Сохранять только `KEEP`, то есть личные настройки (лучше перенести их в `Settings`). Баланс сохранять только из панели F1 и только в отладочной сборке, в отдельный файл. Ключи запуска — через временный слой, который не пишется.

8. **Автотест и скриншоты меняют настоящий профиль игрока** — `tools/ci/smoke.sh`, `full.sh`, `main_debug.gd:500-507`.
   - **Что не так.** Тесты запускают Godot без отдельной папки `user://`. `--shots` добавляет 8000 запчастей, открывает все операции, повышает экипаж и покупает самолёт ур. 2. Каждый вылет автотеста начисляет награду (`Profile.award_run` → `save`), меняет выбранную операцию, счётчики подсказок и `tuning.json`.
   - **Чем грозит.** На компьютере участника портится его профиль. Результат теста зависит от того, что осталось от прошлого запуска (звание, ветки, мета), — тест не воспроизводим.
   - **Как чинить.** В скриптах `XDG_DATA_HOME`/`HOME` во временную папку (Linux) либо ключ `--profile-dir=` с подменой путей в `Profile`, `Campaign`, `Settings`, `Tuning`, `Hints` (всё через одну функцию `SaveIO.path(name)`).

9. **Очередь отчётов анкеты может навсегда остановиться на одном сообщении** — `report.gd:479-555`.
   - **Что не так.** Отправляется всегда `q[0]`. Если приёмник постоянно отвергает именно его (слишком большой `log_tail`, `bad token`), все следующие отчёты не уходят никогда. Очередь `report_queue.json`, в отличие от `run_queue`, ничем не ограничена, а в каждом элементе по 150 строк журнала.
   - **Что ещё.** Успехом считаются любые коды 3xx (`report.gd:449`, `:535`). Если у веб-приложения Apps Script поменяется доступ, Google ответит 302 на страницу входа, и отчёт удалится из очереди как отправленный.
   - **Как чинить.** Ограничить очередь и число попыток на одно сообщение (с отметкой и сдвигом в конец). Успех считать только по телу ответа (`ok`) или по `Location` на `script.googleusercontent.com`.

10. **Переназначение клавиши стирает дублирующую клавишу** — `settings.gd:218-234`.
    - **Что не так.** `rebind` удаляет все события-клавиши действия: переназначили «Вверх» — пропала стрелка ↑. `_defaults` хранит только первую клавишу, поэтому «Сбросить» до перезапуска стрелки не вернёт. Повторы не проверяются: клавиша остаётся и у другого действия.
    - **Как чинить.** Хранить переназначение как «основная клавиша», остальные события не трогать. При совпадении предупреждать или менять местами.

11. **`Main` — глобальный объект на всё** — `main.gd:7` (`static var I`).
    - **Масштаб.** 657 обращений `Main.I` в 46 файлах (чаще всего `.sfx`, `.player`, `.projectiles`, `.fx`, `.tele`). Чужой код прямо меняет поля состояния вылета: `m.pending_levels += 1`, `m.rare_picks`, `m.parts` (`class_task.gd:153-156`), `Main.I.parts` (`cards.gd`), `Profile.cls(c)["perks"] = []` прямо из ввода (`main_input.gd:301`).
    - **Чем грозит.** Любое изменение состояния вылета расходится по 46 файлам. Тестировать логику отдельно нельзя. Отсюда и пункт 1: одни и те же правила выдачи карточек дублируются в 4 местах.
    - **Как чинить.** Вынести состояние вылета в `RunState` (уровень, опыт, запчасти, награды, `grant_rare_pick(reason)`). Сервисы (`sfx`, `fx`) передавать явно либо через узкий интерфейс. Новый код — без `Main.I.<поле> =`.

12. **Числа баланса живут вне `tuning.gd`, вопреки правилу проекта.**
    - **Где.** Опыт за вылет (20/мин, 5×уровень, 60 за аса, 20 за активность, ×0,75 за гибель, 30 за вылет — `profile.gd:586-610`). Прирост узлов и экипажа (`profile.gd:650-667`, причём дублирует тексты в `NODES` и `CREW`). Падение опыта после 5:00 (`main.gd:368-370`, добавлено 23.10, S10-13). Добыча после 15:00 (`main.gd:667`), награды за активность (`main.gd:561-565`), сложности (`campaign.gd:11-16`), эффекты модулей (`cards.gd:897-950`).
    - **Чем грозит.** Методика баланса (R-10, лог «было → стало») требует одного места, а тексты карточек с числами (`prog.gd:218-256`) могут разойтись с кодом.
    - **Как чинить.** Либо `tuning.gd` объявить только «ручками для панели F1», а правило переписать на «данные баланса — в `data/*.gd` или `.tres`». Либо постепенно переносить. Решение за Kanta.

13. **Временные значения теста в коде вылета** — `main.gd:51`, `:247-248`.
    - **Что не так.** `TEST_PICKS := 10` перебросов и исключений «на время тестов» вместо 2. Плюс `Profile.TEST_BUILD := true` (`profile.gd:8`) — мёртвая константа.
    - **Почему важно.** Если не вернуть перед демо, баланс выбора карточек будет не тот.
    - **Как чинить.** Значение в `Tuning` и пункт в чек-листе демо.

#### Мелкие

14. Номер операции в итогах считается глобально: `"n": index() + 1` (`campaign.gd:210`). Для Архипелага игрок видит «Операция 5–8 … пройдена» (`hud_screens.gd:823-829`). Нужно `num()`.
15. `hint_buy` проверяет `lv < 5` (`profile.gd:549`), а не `Demo.node_cap()`. В демо на экране итогов предлагается «Планер ур. 3», которого не купить.
16. В демо с сохранением полной игры `crew_lvl` ограничен 5, а `perks` — нет: `perk_points` уходит в минус (`profile.gd:337`), а перки 2-й ступени (с ур. 6) продолжают действовать (`has_perk`, `profile.gd:340`).
17. `TuningPanel.toggle` ставит `get_tree().paused = visible` (`tuning_panel.gd:93`). Если закрыть панель в состоянии `paused`, мир едет под меню паузы (только отладка).
18. `Campaign.on_baron_met` не вызывает `_load()` (`campaign.gd:172`) и упадёт на `null`, если будет вызвана первой.
19. Подсказки и строка управления написаны с жёсткими клавишами: «Space — уклонение», «Мышь — куда лететь» (`main.gd:240`, `:751`, `hud_flight.gd:49`). Они не учитывают переназначение и геймпад (Steam Deck). Нужно `Settings.key_name(action)` и подписи для геймпада.
20. В баннере награды за активность `+60`/`+100` без `continue_mult()` (`main.gd:567`): после 15:00 начисляется больше, чем написано.
21. Ключи `--god`, `--turbo`, `--report-url` действуют и в тестерской или релизной сборке (`main.gd:116-135`). Для одиночной игры это не дыра, но в релизе лучше пускать только под `DEBUG`.
22. Каждый кадр: `boss_alive()` обходит `get_nodes_in_group("enemies")` с приведением `as Enemy` без проверки типа (`main.gd:313`, `:593-597`). Рядом, в `:610`, проверка `is Enemy` есть. Лучше считать боссов в `Spawner` счётчиком.
23. `Telemetry.frame`: каждый кадр собирается строка ключа (`"tilt%d_s"`, `_device + "_s"`, `telemetry.gd:109-110`), а `_frames` растёт без предела (~130 тыс. значений за 15 мин при 144 к/с). На производительность почти не влияет, но это лишние выделения памяти в горячем пути.
24. `start_run()` делает `world.queue_free()`, и старые враги до конца кадра ещё лежат в группе `enemies` (`main.gd:179-180`). Сейчас безвредно, но коварно для кода, который ищет врагов через группы.
25. `Hints.show`/`bump` и `Campaign.select` пишут файл на каждый вызов, в том числе во время боя (`hints.gd:179`, `:207`). Лучше копить изменения и писать на смене состояния.
26. Текст анкеты отчёта жёстко на русском (`report.gd:23-36`, `:288-296`), а у внешних тестеров есть EN-перевод. Подписи `Label` переведутся автоматически, только если фразы есть в `.po`.
27. `REPORT_URL_BUILTIN` и токены (`report.gd:8`, `:12`) лежат в репозитории. Это не секрет: любой, у кого есть адрес, пишет в таблицу. Если репозиторий станет публичным, адрес сменить.

### Фактические соглашения в коде

- **Язык.** Комментарии и `##`-описания по-русски, с номером правки или задачи в начале: «правка 30», «S9-02», «EX-07», «3.5:» (`main.gd:31`, `profile.gd:344-346`). Это история, а не описание: в `main.gd:35` в одной строке три устаревших комментария.
- **Имена.** `snake_case` для функций и полей, `UPPER_CASE` для констант, `_` — внутреннее (`_load`, `_cfg`). Классы — `class_name` в PascalCase на каждом файле, кроме автозагрузок (`Tuning`, `Settings`, `Profile`, `InputSetup` — без `class_name`). Нарушение: короткие имена полей (`m`, `p`, `v`, `k`, `L` — `profile.gd:647`).
- **Три вида модулей.**
  - Автозагрузки (`extends Node`): `Tuning`, `Settings`, `Profile`, `InputSetup`.
  - Статические модули `class_name X extends RefCounted` со `static var` для состояния: `Campaign`, `Story`, `Hints`, `Demo`, `Loc`, `Prog`, `PlaneClasses`. Их состояние живёт весь сеанс, а `Story` сбрасывается в `start()` вручную.
  - Помощники `Main` (`MainInput`, `MainDebug`) — `RefCounted` с полем `m`.
- **Данные — словари-константы** с позиционными массивами: `WBRANCH[w][tier][0|1][2]` (`profile.gd:27-40`), `PERKS` вида `[название, [[id, имя, текст], …]]` (`profile.gd:91-107`), обращения вида `br[1][1][0]` (`profile.gd:502-510`). Читается тяжело, ошибка индекса не ловится до запуска.
- **Состояния игры — строки** (`"menu"`, `"playing"`, `"levelup"`, `"course_pick"`, `main.gd:25-26`), смена — `_set_state` с паузой дерева. Список состояний в комментарии неполон: нет `hangar`, `codex`, `course_pick`.
- **Действия UI — строки с двоеточиями**, разбор цепочкой `elif` (`main_input.gd:160-256`): `"hg:node:frame:2"`, `"card:1"`. Ошибка в строке молча ничего не делает.
- **Интерфейс рисуется кодом**: сцены только `main.tscn` (6 строк), всё остальное создаётся в `_ready` (`report.gd:81-178`) или рисуется `draw_*` (HUD). Цвета — константы `Menu.C_AMBER`, `C_DIM`, но рядом много прямых `Color(0.08, 0.07, 0.05)`.
- **Типизация частичная.** Сигнатуры обычно типизированы (`-> void`, `: String`), локальные через `:=`. Но JSON и данные идут как `var d = …` и `Array` без типа элементов. Встречается `for e: Dictionary in` (`run_log.gd:78`) и `Array[Button]` (`report.gd:189`), но редко.
- **Сохранения.** JSON для `profile`, `settings`, `tuning`, очередей; `ConfigFile` для `campaign.cfg` и `hints.cfg`; обычный текст для `tester_id`. Атомарная запись — только у профиля. Общего слоя нет, у каждого модуля свой `PATH` и свой `_load`/`save`.
- **Перевод.** `Loc.t()` для шаблонов с `%`; простые строки пишутся по-русски как есть и переводятся на выводе (`Loc.out` при рисовании, автоперевод `Label`). Непоследовательно: в `profile.gd:260-272` часть строк через `Loc.t`, часть нет (`:265-269`).
- **Ключи запуска** читаются в разных местах по-разному: `Main._args` (`main.gd:114`) и прямой `OS.get_cmdline_user_args()` (`main.gd:657`, `class_task.gd:161`, `spawner.gd:36-41`, `demo.gd:26`).
- **Отладка.** `Main.DEBUG` (статическая, вычисляется в `Main._ready` по фиче `tester`) закрывает F1/F4–F8 и кнопки ангара. Сами `hg:dbg_*` в `hangar_action` (`main_input.gd:319-326`) не проверяют `DEBUG`: защищает только то, что кнопки не рисуются.
- **Размер файлов.** Ядро в пределах (`main.gd` 826, `profile.gd` 745), но `cards.gd` 998, а в проекте есть `render3d.gd` 2565, `adobe_build.gd` 1530, `terrain3d.gd` 1464.

### Рекомендации для стандартов кода и архитектуры

1. **Слой сохранений `SaveIO`**: атомарная запись с проверкой, `.bak`, восстановление, `version` и миграции, одна функция пути (для подмены папки в тестах), список файлов для Steam Cloud. Все `user://`-файлы — через него.
2. **`RunState` отдельно от `Main`**: состояние вылета и операции над ним (`add_xp`, `grant_rare_pick`, `refill_offers`, `award`) в одном классе, который можно проверить без сцены. `Main` — только сборка узлов и переходы состояний. Правило: чужой код не пишет поля `Main.I`.
3. **Состояния и действия — `enum` или константы**, а не голые строки. Таблица переходов (из какого состояния куда и что делает Esc) — в одном месте, с обязательным выходом из каждого экрана.
4. **Данные баланса**: решить, где лежат числа (только `tuning.gd` или `data/`), и что в `tuning.json` пишутся только личные настройки. Тексты карточек с числами строить из тех же констант.
5. **Именованные поля вместо позиционных массивов** в данных (`{"id":…, "title":…, "desc":…}`) — меньше ошибок с индексами при правках геймдизайнера.
6. **Комментарии**: в коде — что и почему сейчас. История правок («было 1 с», номера правок) — в коммитах и `docs/`. Номер задачи — одна ссылка в конце.
7. **Конфиденциальность**: любая отправка по сети — только при согласии, флаг в `Settings`, постоянный `tester_id` — только в тестерских сборках. Описание полей отчёта — в политике на сайте.
8. **Тесты в отдельной папке `user://`** (`smoke.sh` и `full.sh` с временным `HOME`), и сценарий автотеста на «пул карточек пуст».
9. **Версия сборки — одно место в репозитории**, коммитом перед экспортом.
10. **Ключи запуска** читать через одну функцию `Args.has()`, отладочные пускать только при `Main.DEBUG`.
11. **Подсказки и подписи клавиш** строить из `InputMap`, а не писать клавиши текстом.

### Отложено

- `perf.gd` — включается только `--perf`, на игроков не влияет. Прочитан только список членов.
- `cards.gd` за пределами `offer`/`apply` — правила выдачи и редкость по сути геймдизайн, судить без методики баланса не стал.
- `main_debug.gd` целиком (autotest-бот, скриншоты) — инструмент разработки; проверено только влияние на профиль.
- Приёмник отчётов (`tools/reports/`, Apps Script) — вне области; проверена только клиентская сторона.
- Поведение `DirAccess.rename` на macOS и Linux (там `rename` атомарен) — критичность пункта 2 в основном для Windows.
- Попадают ли в `godot.log` (уходит в отчёте, 150 строк) абсолютные пути с именем пользователя ОС — не проверял на реальном журнале. Стоит посмотреть один журнал тестера перед публикацией политики.
- `menu.gd` и HUD, кроме мест, связанных с данными, — не моя область.

### Итог

Ядро аккуратно для прототипа: покупки защищены проверками, профиль пишется через временный файл, телеметрия богатая, демо-режим сделан одной точкой. До демо и раннего доступа обязательно нужны три вещи:
- выход из пустого экрана выбора карточек;
- восстановление профиля после сбоя записи и при битом файле;
- согласие игрока на автоматическую отправку строк вылета.

Главный архитектурный долг — `Main.I` как общий объект состояния для 46 файлов и числа баланса, разбросанные вне `tuning.gd`.
