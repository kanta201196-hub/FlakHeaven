Принятые правила плейбука с поправками — в `CLAUDE.md` и `docs/process/project-instructions.md`; при расхождении верны они.

Oct 16, 2026 · @Ekaterina

Этот плейбук собирает правила, которые сложились на Flak Heaven за 14–16.10.2026, и переносит их на следующую игру, чтобы не наступать на те же грабли с первого дня.

Как пользоваться: в первый день нового проекта пройти чек-лист из раздела «Чек-лист первого дня», вставить готовый блок инструкций в настройки проекта и положить этот документ в папку проекта. Правила меняются только с «да» владельца; что изменилось, дописывается в «Уроки» с датой.

## 1. Главные принципы

1. **Решения принимает владелец.** Геймдизайн, арт, звук, деньги, юридика, состав команды — только с её «да». Claude готовит варианты и свою рекомендацию.
2. **Сначала предложение, потом изменение.** Крупные правки правил, структуры или настроек сначала показываются как предложение. Обратимую мелочь (черновик, ветка, файл) Claude делает сам и пишет, какой вариант выбрал.
3. **Документы — источник правды.** Решение → журнал решений в `docs/game-context.md`, задача → `docs/backlog.md`, итог сборки → `docs/status-log.md`. Чего нет в документах и памяти проекта, того новый Claude не знает.
4. **Всё по-русски.** Ответы, статусы, названия тредов, пункты меню игры. Кнопки GitHub цитируются так, как они видны на экране: «Merge pull request», «Confirm merge». Имена файлов и папок — только латиницей.
5. **Каждое действие владельца — с прямой ссылкой.** На PR, файл, страницу настроек или сайт. Нет ссылки — точно где нажать.
6. **Вымышленный мир.** Без реальных стран, флагов, опознавательных знаков, брендов и названий реальной техники. Техника и места — «по мотивам», опознавательные знаки стираются до генерации моделей.
7. **Деньги — только на инструменты и подписки, решение за владельцем.** Ограничения сервисов и регионов не обходим. Удаление файлов на компьютере владельца — только с её разрешения.
8. **Сборка — только по прямой задаче.** Нет задачи на архив / exe / app — сначала спросить.

## 2. Как мы общаемся

- **Правки пачками.** Владелец присылает замечания частями, Claude их собирает в пронумерованный список и начинает работу только после слова «готово».
- **Вопросы текстом с номерами.** Карточки с выбором могут не отображаться, поэтому каждый вопрос дублируется в ответе: «1 — …, 2 — … (рекомендую 1)». Ответить можно цифрой, несколько сразу: «3, 4 да, 5 нет».
- **Ответ начинается с того, что нужно от владельца.** Дальше результат, без пересказа хода работы. Длинное (больше 15 строк) — файлом или документом со ссылкой.
- **Мало открытых тредов.** Один тред — одна система или тема («ИИ врагов», «3D и биом», «Прокачка»). Новая задача по теме идёт в существующий тред. Тред закрывается, когда его работа слита или заменена.
- **Один живой файл статуса.** Каждый тред обновляет свою строку при открытии и слиянии PR. Тогда на «актуализируй статус» ответ даётся сразу, без обхода тредов.
- **Планёрка раз в день, ультракороткая.** В фиксированное время (у нас \~17:00 МСК), отдельным тредом: что сделано, что ждёт владельца (со ссылками), решения без исполнителя. Раз в неделю — чек-лист владельца (Steam, юридика, финансы) с дедлайнами.
- **Второе мнение — совет, не решение.** Кросс-проверка в GPT или Gemini полезна для крупных документов (концепция, механика полёта), её выводы разбираются по пунктам и идут на решение владельцу.

## 3. У каждого решения есть исполнитель

Решение без исполнителя теряется: «бой в 3D» решили 14.10, а в работу оно попало только 16.10. Поэтому каждое «да» проходит один и тот же путь:

1. Запись в журнал решений: дата, что решено, почему.
2. Задача в бэклоге с номером, номер ставится в запись журнала.
3. Тред-владелец назначается сразу (существующий или новый) и пишется в задаче.
4. Планёрка каждый день одной строкой называет решения без владельца.
5. Важные долговременные решения и предпочтения владельца ещё и в память проекта, чтобы новые треды их знали.

Для крупного пересмотра (каталог техники, плейтест) работает петля из каталога: документ с картинками → замечания владельца по пунктам → план исполнения с её ответами → распределение пунктов по тредам → статус по каждому пункту в одном файле.

## 4. Код и Git

- **Одна общая ветка `next` с первого дня.** Треды сливают свои ветки в `next` сами и сами решают конфликты. Владелец раз в день (или перед тестовой сборкой) сливает один PR `next` → `main` со списком вошедшего. На Flak Heaven за два дня было 12 отдельных слияний и 4 расхождения веток.
- **Claude не сливает в `main` сам.** Проверка прав не даёт сливать PR без ревью. Вместо обещания «скажи да и солью» — ссылка на PR и кнопки «Merge pull request» → «Confirm merge».
- **Автопроверка на GitHub (CI) до первого PR.** GitHub Actions на каждый PR: импорт проекта и быстрый автотест без окна. Зелёная галочка — можно сливать, красную тред чинит сам.
- **Два автотеста.** Быстрый (2–3 минуты: один класс, короткий бой, нет ошибок скрипта, пара скриншотов) — после каждой правки. Полный — один раз перед PR. Для правок вне боя (меню, документы) хватает проверки синтаксиса. Полный прогон на каждую правку стоил 15–30+ минут и лимита.
- **Маленькие файлы с одним владельцем.** Каждая система (полёт, оружие, ведомые, ИИ, интерфейс) — в своём файле. Файл больше \~500 строк — сигнал разделить. `player.gd` на 1248 строк правили 3–4 треда сразу. В задаче бэклога пишется, какой тред владеет файлом.
- **Все числа баланса в одном файле** (у нас `tuning.gd`), а флаги отладки выключаются одной фичей тестовой сборки.
- **Коммит маленький, описание по-русски:** что и зачем. Не коммитим служебные папки движка, сборки, личные логи, ключи.
- **`CLAUDE.md` в корне репозитория** с картой папок, правилами и командами проверки. Раздел «Текущее состояние» обновляется при каждой сборке.

## 5. Тестовые сборки и телеметрия

- **Сборка сама собирает данные.** Лог вылета пишет влияние каждой изменённой системы: FPS, нагрузка 3D, поведение ИИ, баланс. У лога есть версия формата (у нас `l4`, `l5`).
- **Лог уходит сам вместе с отчётом тестера** (в Google Таблицу через Apps Script). Искать файлы в `%APPDATA%` и прикладывать их вручную внешние тестеры не будут. Треды читают таблицу сами через коннектор Google Drive.
- **Производительность — только по реальным ПК.** FPS в облаке без видеокарты ничего не значит. Цель фиксируется сразу (у нас 40 FPS на слабом ПК).
- **Номер сборки в коде и в имени архива** (`3.4-t1`), сборки сразу для Windows и Mac с инструкцией для тестера.
- **После теста — пронумерованный список правок** с одним файлом статусов: номер, тред, PR, состояние.

## 6. Арт и 3D

Инструмент выбирается по типу объекта: на Flak Heaven простые детали из генератора пришлось переделывать, а Blender по фото владельца дал лучший результат.

| Что делаем | Инструмент | Почему |
| --- | --- | --- |
| Сложные формы: самолёты, крупная техника, скалы | Генератор 3D (Meshy, \~30 кредитов за модель) | Быстро даёт объём и фактуру |
| Простые и точные детали: турели, оружие, ракеты, ПВО | Blender кодом в облаке по референсам владельца | Точная форма, дёшево, файл .blend можно править |
| Портреты, концепты, референсы | ChatGPT или Gemini по готовым промптам от Claude | Владелец выбирает лучший вариант сам |
| Текстуры земли и камня | Бесплатные CC0 (Poly Haven, ambientCG) | Без лицензионных рисков |

Правила:

- **Каталог до моделей.** Сначала список всей техники и оружия с картинками, владелец даёт замечания и референсы (папка `refs/` по типам), потом модели.
- **Входная картинка утверждается до траты кредитов:** вид, силуэт «по мотивам», без опознавательных знаков. Перед пакетом — баланс и сколько уйдёт.
- **Два уровня качества.** В бою облегчённые модели (\~5–15 тыс. треугольников), в ангаре и крупных планах — максимальные. Исходники храним всегда.
- **Предпросмотр из игровой камеры.** Каждая модель показывается владельцу скриншотом так, как её увидит игрок.
- **Коммерческие условия генератора проверяются до первой модели**, а не перед Steam.

## 7. Ресурсы Claude

Лимит использования заканчивался дважды (15.10 и 16.10, оба раза вечером), когда пять тредов на самой сильной модели одновременно гоняли длинные автотесты.

- **Модель по задаче.** Сильная (Opus) — код игры, геймдизайн, 3D в Blender. Лёгкая (Sonnet) — статусы, сводки, планёрка, документы, сборки архивов, регулярные задачи. Claude переключает сам, если качество не падает, и спрашивает только в спорных случаях.
- **Не больше 3 тредов с кодом одновременно.** Остальные ждут в очереди бэклога: это и лимит, и меньше конфликтов.
- **Длинные процессы — в фоне.** Автотест, экспорт, генерация моделей запускаются и не держат тред активным всё время.
- **Тяжёлую работу ставим на утро и день**, чтобы к вечеру, когда владелец смотрит результаты, лимит оставался.

## 8. Окружение и устройства

- **Скрипт установки в облачной среде.** Движок нужной версии, шаблоны экспорта, Blender (`bpy`), библиотеки для 3D ставятся при старте треда. Иначе каждый тред тратит 5–10 минут и иногда ломается до начала работы.
- **Сетевой доступ и ключи заранее.** Домены сервисов (генератор 3D, текстуры CC0, Gemini) и переменные с ключами добавляются до первого треда: изменения среды обычно доходят только до новых тредов. Для Gemini нужен ключ API из AI Studio, подписка в приложении для автоматизации не подходит.
- **Один компьютер по умолчанию.** Тот, на котором владелец играет в тестовые сборки, с разрешённой папкой игры. На Flak Heaven ни один не был выбран основным, поэтому карточки подключения не срабатывали и логи приходилось прикладывать вручную.
- **Папка проекта с постоянной структурой:** `concept/`, `catalog/` (+ `refs/`), `builds/`, `playtest/<сборка>/`, `process/`, `owner-checklist/`, `uploads/`. Большие файлы (модели, архивы) там, а не в репозитории.

## 9. Инструкции проекта для вставки

Блок ниже копируется целиком в настройки нового проекта (поле инструкций проекта). Вместо `<…>` подставить своё.

```markdown
Пиши по-русски: ответы, статусы, названия тредов, пункты меню и кнопки игры. Кнопки GitHub цитируй так, как они видны на экране. Имена файлов и папок — только латиницей.

Игра: <название>, <жанр, движок и версия>, цель — <Steam / ранний доступ / дата>. Репозиторий: <ссылка>. Правила для кода — в CLAUDE.md в корне репозитория.

Решения (геймдизайн, арт, звук, деньги, юридика) принимает владелец. Ты готовишь варианты и свою рекомендацию. Крупные изменения правил и настроек сначала показывай как предложение.

Вопросы задавай текстом с номерами вариантов и своей рекомендацией, чтобы можно было ответить цифрой. Карточка с выбором — только дополнение, не единственное место вопроса.

Когда от владельца нужно действие (слить PR, посмотреть файл, поменять настройку), давай прямую ссылку туда, где оно делается. Если ссылки нет, коротко напиши, где нажать. Не обещай слить PR сам: давай ссылку на PR и пиши, что внизу страницы нужно нажать «Merge pull request», затем «Confirm merge».

Правки я присылаю частями. Собирай их в пронумерованный список и начинай работу после моего «готово».

Каждое решение: запись в журнал решений, задача в бэклоге с номером и тред-исполнитель сразу. Планёрка раз в день в <время> МСК, ультракоротко: сделано, ждёт меня (со ссылками), решения без исполнителя.

Держи мало открытых тредов: один тред на систему, закрывай тред, когда его работа слита. Не больше 3 тредов с кодом одновременно. Статус всех правок — в одном файле, каждый тред обновляет свою строку.

Модели: код и дизайн — сильная модель; статусы, сводки, документы, сборки и регулярные задачи — лёгкая. Переключай сам, если качество не падает. Длинные автотесты запускай в фоне.

Работа в Git: треды сливают свои ветки в общую ветку next и сами решают конфликты; раз в день готовь мне один PR next → main со списком вошедшего. Перед PR — полный автотест и зелёная автопроверка GitHub. Новую сборку для тестеров делай только по прямой задаче.

Тестовые сборки логируют влияние всех изменений и отправляют лог вместе с отчётом тестера. Производительность оценивай только по логам с реальных ПК.

Мир игры вымышленный: без реальных стран, флагов, опознавательных знаков и названий реальной техники; всё «по мотивам». Деньги тратятся только с моего решения; кредиты генераторов береги: простые детали делай в Blender по моим референсам, входную картинку для генератора сначала показывай мне.
```

## 10. Чек-лист первого дня новой игры

Проект и настройки (делает владелец):

- [ ] Создать проект и вставить инструкции из раздела 9
- [ ] Создать репозиторий на GitHub, установить приложение Claude, подключить репозиторий к проекту
- [ ] Включить GitHub Actions в настройках репозитория
- [ ] Облачная среда: сетевой доступ к нужным сервисам, ключи API (генератор 3D, Gemini), скрипт установки (присылает Claude)
- [ ] Выбрать один компьютер по умолчанию и разрешить папку игры
- [ ] Подключить Google Drive (отчёты тестеров) и проверить условия коммерческого использования всех генераторов

Каркас проекта (делает Claude, владелец утверждает):

- [ ] `CLAUDE.md`: что за игра, карта папок, правила, команды проверки, текущее состояние
- [ ] Документы: концепция с журналом решений, бэклог, журнал сборок, чек-лист владельца (Steam, юридика, финансы)
- [ ] Ветки `main` и `next`, автопроверка на каждый PR, быстрый и полный автотест
- [ ] Структура кода: системы в отдельных файлах, все числа баланса в одном файле, флаги отладки
- [ ] Лог вылета с версией формата и отправка отчёта тестера вместе с логом
- [ ] Пресеты экспорта Windows и Mac и инструкции для тестеров
- [ ] Память проекта: предпочтения владельца из этого плейбука

Решения первой недели (владелец отвечает цифрами):

- [ ] Движок, рендер и целевой FPS на слабом ПК
- [ ] 2D или 3D в бою, сразу с тредом-исполнителем
- [ ] Стиль арта и генераторы; каталог объектов до первой модели
- [ ] Объём раннего доступа (сколько биомов и боссов) и концепция всех биомов хотя бы в один абзац
- [ ] Музыка и звук в плане с первого спринта
- [ ] Даты: страница в Steam, Next Fest, ранний доступ; банк и оплата для Steamworks как первый риск
